# psippr-desktop deb: host-impact audit

- **Date:** 2026-10-09
- **Audited artifact:** `packages/main-release/deb/psippr-desktop_1.0.5_amd64.deb` (built 2026-10-09 08:06, HEAD `e9fb4707`)
- **Sources audited:** `buildSrc/src/main/kotlin/PackageFullDebTask.kt`, `session/*`, `session/debian/*`,
  `build.gradle.kts` (`packageFullDeb`), `compositor/compositor.gradle.kts` (`installDesktop`, `installSession`),
  `gradle/libs.versions.toml`, and the runtime code of the installed app that writes outside its own
  directories (theme manager, data migration, font guard).
- **Reference host:** this machine (Ubuntu, GDM3, psippr-desktop 1.0.4 installed, greetd 0.10.3 installed).
- **Method:** I read the code and extracted the real control archive with `dpkg-deb -e`. I installed
  nothing, ran nothing as root and changed nothing on the host.

---

## 1. Verdict

The deb contains **no malicious code**: no payload download, no network calls from the maintainer
scripts, no deletion of user data, and no files written outside the package's own scope apart from
the items listed below.

It does contain **real defects that can damage the host configuration**, mostly the graphical login
(display manager) and the user's GNOME/GTK appearance. Nothing is physically destroyed. Every case
can be recovered from a text console, but some of them can leave a machine **without a working
graphical login** after a reboot.

| # | Finding | Severity | Can break the host? |
|---|---|---|---|
| F1 | Choosing "psippr-desktop" in the display-manager dialog makes the psippr greeter the boot login. The greeter is known to be non-working. | **High** | Yes: no graphical login after reboot |
| F2 | Removing or purging the package never restores the previous display manager | **High** | Yes: dangling `display-manager.service` → boots to console |
| F3 | Hard `Depends: greetd`. greetd's own postinst enables it as `display-manager.service`, and the repair only runs under some conditions | Medium | Yes, on hosts where the repair conditions fail |
| F4 | A greetd drop-in overrides **any** greetd setup on the host, even when psippr is not chosen | Medium | Breaks an existing greetd/tuigreet setup |
| F5 | Files in `/etc` are shipped without `DEBIAN/conffiles` | Medium | Admin edits silently lost; Debian policy violation |
| F6 | The runtime app rewrites `~/.config/gtk-{3,4}.0/gtk.css` and GNOME gsettings with no persistent backup, and deletes those files on exit | Medium | Changes and loses the user's GNOME/GTK look (**confirmed on this host**) |
| F7 | `_greetd` is added to the `video,input,render` groups and this is never undone | Low–Medium (security) | Gives the greeter account raw input access permanently |
| F8 | Postinst `rm -f` of hardcoded legacy paths in `/usr/local/bin` and `/usr/share` | Low | Only mjdev/psippr-named files |
| F9 | Data migration moves `~/.psippr/desktop` and `~/.psippr/plugins`, which belong to the separate *psippr* project's folder | Low–Medium | Can take data away from the other project |
| F10 | `installDesktop` (dev task, not the deb) installs duplicate binaries to `/usr/local/bin`, which shadow the deb's `/usr/bin`. It also adds the user to `input`/`video`/`render`/`seat` and starts seatd | Medium (dev hosts) | Stale compositor after a deb-only upgrade; keylogging-capable group membership |
| F11 | The original jpackage postinst is replaced. The prerm still runs `xdg-desktop-menu uninstall` under `set -e` | Low | No app-menu entry; prerm could block removal (not verified) |
| F12 | `Provides: x-display-manager` | Low | apt treats psippr as a real DM and may not keep or pull a working one |

## 2. What the deb installs

Control fields of the built deb:

```
Package: psippr-desktop   Version: 1.0.5
Provides: psippr-desktop, mjdev-desktop, x-display-manager
Replaces: mjdev-desktop   Conflicts: mjdev-desktop
Recommends: seatd
Depends: <jpackage libs…>, libwlroots-0.18, xwayland, libegl1, libgles2, libgbm1, libinput10,
         libseat1, libxkbcommon0, libgl1-mesa-dri, dbus, dbus-user-session, greetd
```

Files outside `/opt/psippr-desktop`:

| Path | Purpose |
|---|---|
| `/usr/bin/psipprc` | Wayland compositor (Kotlin/Native + wlroots) |
| `/usr/bin/psippr-session` | session launcher |
| `/usr/bin/psippr-greeter` | greetd greeter launcher |
| `/usr/share/wayland-sessions/psippr.desktop` | session entry shown by GDM/SDDM/… |
| `/etc/psippr-desktop/greetd.toml` | greetd config (greeter = psippr-greeter, user `_greetd`, VT7) |
| `/etc/systemd/system/greetd.service.d/psippr.conf` | **drop-in that replaces greetd's `ExecStart`** |

Maintainer scripts: `config` + `templates` (debconf "Default display manager" question), `postinst`
(generated by `PackageFullDebTask.writePostinst` + `session/debian/postinst-dm`), and the jpackage
defaults `preinst`, `prerm` and `postrm` (no-ops except the prerm `xdg-desktop-menu uninstall`).
**There is no `conffiles`.**

## 3. Findings in detail

### F1: The psippr greeter becomes the boot login (High)

`session/debian/postinst-dm` lines 6–10. When the user picks `psippr-desktop` in the debconf
dialog (shown at `high` priority on every interactive install):

```sh
echo /usr/sbin/greetd > /etc/X11/default-display-manager
ln -sf /usr/lib/systemd/system/greetd.service /etc/systemd/system/display-manager.service
```

At the next boot greetd runs `/usr/bin/psippr-greeter` (via the drop-in), which starts `psipprc`
plus the full JVM desktop as the `_greetd` user. According to `ai-damaged-code.txt`, the greeter
**does not work** (no user list, a login that cannot complete). `greetd.service` has
`Restart=always` / `RestartSec=1`, so a failing greeter restarts in a loop on VT7.

- **Impact:** after a reboot there is no usable graphical login. The system itself is intact.
- **Recovery:** Ctrl+Alt+F3 → log in on the text console → `sudo dpkg-reconfigure gdm3` (or lightdm/sddm)
  and choose the old display manager → reboot.
- **Root cause:** the package offers itself as a display manager although the greeter has not been
  verified to work on real hardware or in the ISO.

### F2: Removal does not restore the previous display manager (High)

`postrm` is the jpackage default and does nothing. After F1, `apt remove psippr-desktop` leaves:

- `/etc/X11/default-display-manager` → `/usr/sbin/greetd`
- `/etc/systemd/system/display-manager.service` → `greetd.service`
- the drop-in is removed with the package, so greetd falls back to `/etc/greetd/config.toml`
  (a text greeter);
- greetd was installed only as a dependency, so `apt autoremove` removes it. The
  `display-manager.service` link then **dangles** and the machine boots without any graphical login.

The debconf owner of `shared/default-x-display-manager` is also not purged (no `db_purge`), so
"psippr-desktop" can stay listed as a choice in other display managers' dialogs after purge.

- **Recovery:** same as F1.

### F3: Hard dependency on greetd and the display-manager alias race (Medium)

greetd is a hard `Depends`, so it is installed on every host, even when the user never selects
it. greetd's own postinst (verified on this host in `/var/lib/dpkg/info/greetd.postinst`) runs
`deb-systemd-helper enable greetd.service`, and `greetd.service` has `Alias=display-manager.service`.

`postinst-dm` lines 11–20 try to point the alias back. This happens **only** if all of these hold:

1. `/etc/X11/default-display-manager` exists and is non-empty;
2. the basename of the binary named there matches a unit `/usr/lib/systemd/system/<name>.service`;
3. the current link points to `greetd.service`.

If any of these fails (no display manager installed yet, a non-Debian-style DM, a unit name that
differs from the binary name, `/lib` vs `/usr/lib` layouts without merged-usr), greetd stays as
`display-manager.service`. On a graphical-target host the psippr greeter (F1) then starts at boot
**even though the user never chose it**.

On **this** host the repair works: `gdm3.service` → `gdm.service` exists, the link points to
`gdm3.service`, and greetd is `disabled`.

### F4: The greetd drop-in hijacks any greetd configuration (Medium)

`/etc/systemd/system/greetd.service.d/psippr.conf`:

```ini
[Service]
ExecStart=
ExecStart=/usr/sbin/greetd --config /etc/psippr-desktop/greetd.toml
```

This file is installed unconditionally, not only when psippr is chosen. A host that already uses
greetd (tuigreet, gtkgreet, regreet, …) has its `/etc/greetd/config.toml` ignored from the next
greetd restart and gets the psippr greeter instead. The comment in `psippr-greetd.toml` ("the greetd
package's own config stays untouched") is true for the file, but the effect is the same as replacing it.

**On this host the drop-in is present right now.** It is inactive only because greetd is disabled.

### F5: `/etc` files are not conffiles (Medium)

`PackageFullDebTask` builds with plain `dpkg-deb --build` and writes no `DEBIAN/conffiles`. So
`/etc/psippr-desktop/greetd.toml` and the systemd drop-in are treated as ordinary files: admin
edits are overwritten without a prompt on upgrade and deleted on remove. Debian Policy 10.7.3
requires files in `/etc` to be conffiles, and lintian would report this as an error.

### F6: The runtime app changes the user's GNOME/GTK appearance (Medium, confirmed on this host)

This is not a maintainer script. It is what the installed software does every time it runs: in the
psippr session, in `:desktopApp:run`, and inside GNOME.

- `ThemeManagerLinux.createFromPalette()` runs on every wallpaper palette change
  (`Palette.kt:163`). It writes:
  - `~/.themes/<theme>/…` (its own theme directory, harmless);
  - **`~/.config/gtk-3.0/gtk.css` and `~/.config/gtk-4.0/gtk.css`**. These are the user's global
    GTK override files, used by **every** GTK app in **every** session (GNOME too). Any previous
    content is overwritten with no backup (`ThemeFileWriter.writeIfChanged`).
- `LiveThemeSwitcher.apply()` writes gsettings `org.gnome.desktop.interface color-scheme`,
  `accent-color` and `gtk-theme`, and GNOME Shell `user-theme name`. These live in the user's dconf
  database, which the GNOME session shares.
- I found no check that limits this to the psippr session (GTK files and gsettings are written in
  any session).
- Restore (`clearSystemTheme()`, called from `Palette.dispose()`) depends on:
  - original values held **only in memory** (`previous` map). After a crash, SIGKILL, power loss or
    the compositor being killed, nothing is restored. On the next run the "original" value it reads
    is already the psippr one, so a later restore **resets to the default** instead of the user's
    real setting;
  - **deleting** `~/.config/gtk-{3,4}.0/gtk.css`, so a user's own custom CSS that was there before
    is lost for good.

**Evidence on this host:**

```
$ gsettings get org.gnome.desktop.interface gtk-theme
'Psippr-Desktop'
$ head -1 ~/.config/gtk-3.0/gtk.css ~/.config/gtk-4.0/gtk.css
/* Generated by psippr-desktop from the wallpaper palette - do not edit. */
```

GNOME on this machine is currently running with the psippr-generated theme. I cannot tell from the
disk whether these `gtk.css` files had user content before.

- **Recovery:** `gsettings reset org.gnome.desktop.interface gtk-theme` (also `color-scheme` and
  `accent-color`), and delete or restore `~/.config/gtk-{3,4}.0/gtk.css`.

### F7: The greeter account gets raw input access (Low–Medium, security)

`postinst-dm` line 4: `usermod -aG video,input,render _greetd`. Membership in `input` allows
reading `/dev/input/event*` (every keystroke of every user). The compositor-as-greeter needs it,
but it is never removed on remove or purge. If the `render` group does not exist, the whole
`usermod` fails silently (`|| true`) and the greeter then has no DRM access.

### F8: Unconditional `rm -f` in postinst (Low)

```
rm -f /usr/share/xsessions/psippr-desktop.desktop /usr/share/gnome-session/sessions/psippr-desktop.session
rm -f /usr/local/bin/mjdevc /usr/local/bin/mjdev-session /usr/share/wayland-sessions/mjdev.desktop \
      /usr/share/xsessions/mjdev-desktop.desktop /usr/share/gnome-session/sessions/mjdev-desktop.session \
      /usr/share/applications/mjdev-desktop-mjdev-desktop.desktop
```

All paths belong to this project's old names, so the risk is low. They are deleted without checking
whether another package owns them (`dpkg -S`). Also, `systemctl enable seatd` only enables seatd
(no `--now`), so it is harmless next to logind.

### F9: Data migration touches the other project's folder (Low–Medium)

`LegacyDataDir.kt`: `PsipprConfig(".psippr/desktop" → ".psippr-desktop/desktop")` and
`PsipprPlugins(".psippr/plugins" → ".psippr-desktop/plugins")`. `~/.psippr` is documented in the
same file as possibly belonging to the separate *psippr* project. If that project uses
`~/.psippr/plugins`, its plugins are **moved** (renamed, not deleted) into psippr-desktop's folder
the first time psippr-desktop starts. An earlier version (now commented out) moved `~/.mjdev`
**into** `~/.psippr`, the other project's folder. Installed 1.0.4 may still contain that behaviour.
Both `~/.psippr` and `~/.psippr-desktop` exist on this host.

### F10: `installDesktop` / `installSession` dev tasks (Medium on developer hosts)

These are not part of the deb, but they install it as root via pkexec, so they are relevant:

- `install -Dm755 … /usr/local/bin/psipprc` and `/usr/local/bin/psippr-session`. These files are
  **outside dpkg**: `apt remove` never removes them. Because `/usr/local/bin` comes before
  `/usr/bin` in PATH and both launchers use `command -v psipprc`, a later deb-only upgrade keeps
  running the **stale** `/usr/local/bin/psipprc`. On this host both copies exist and are currently
  identical.
- `usermod -aG video,input,render[,seat] <user>`: the desktop user's own processes can read all
  keyboard input (keylogger-capable).
- `systemctl enable --now seatd`, plus `apt-get update` and `install` with `DEBIAN_FRONTEND=noninteractive`.

### F11: The jpackage postinst is replaced but its prerm is kept (Low)

`writePostinst` replaces jpackage's postinst, which used to run `xdg-desktop-menu install …`. So the
app gets **no application-menu entry**. The jpackage `prerm` still runs
`xdg-desktop-menu uninstall /opt/psippr-desktop/lib/psippr-desktop-psippr-desktop.desktop` under
`set -e`. If that command ever returns non-zero, `dpkg --remove` fails and the package is stuck
half-installed. I did not test this, so it is unconfirmed.

### F12: `Provides: x-display-manager` (Low)

apt treats psippr-desktop as satisfying `x-display-manager`. Removing the only real DM (gdm3) does
not make apt warn or pull another one, because psippr "provides" it, even though the greeter does
not work (F1).

## 4. What the deb does **not** do (checked)

- No network access, download, curl/wget, or telemetry in any maintainer script.
- No `rm -rf`, no deletion in `/home`, `/etc/greetd`, or any other package's files (beyond F8).
- It does not change PAM, sudoers, polkit rules, SSH, the firewall, the bootloader, or the kernel.
- No setuid binaries are added.
- `preinst` and `postrm` are no-ops.
- The font guard writes only to `~/.cache/psippr-desktop/` and uses it through `FONTCONFIG_FILE`
  for its own child process. System and user font config are untouched.
- `psippr-session` only unsets its own variables in the systemd `--user` environment on exit.

## 6. Recommended minimal fixes (not applied; approval needed)

1. **F1/F3/F12:** stop offering psippr as a display manager until the greeter is verified working.
   Make `greetd` a `Suggests` (or a separate `psippr-greeter` package) and drop
   `Provides: x-display-manager`.
2. **F2:** add a `postrm` that, on `remove`/`purge`, restores the previous DM when
   `/etc/X11/default-display-manager` points to greetd (save the old value in postinst), and calls
   `db_purge` on purge.
3. **F4:** install the greetd drop-in only when psippr is chosen (create it in postinst instead of
   shipping it), or point it to a config that greetd uses only if selected.
4. **F5:** write `DEBIAN/conffiles` in `PackageFullDebTask` for every file under `/etc`.
5. **F6:** limit GTK/gsettings writes to the psippr session (`XDG_CURRENT_DESKTOP=psippr`), back up
   the original values and files to disk before the first write, and never delete a `gtk.css` the
   app did not create.
6. **F7:** remove the `_greetd` group additions on purge.
7. **F9:** remove the `~/.psippr/*` migration entries, or move them only after checking the content
   is psippr-desktop's own.
8. **F10:** `installDesktop` should install only via the deb (no `/usr/local/bin` copies) and remove
   existing `/usr/local/bin/psipprc` and `psippr-session`.
9. **F11:** keep jpackage's `xdg-desktop-menu install` in the custom postinst, and make the prerm
   call `|| true`.
